# How an app talks to the database

There is no backend between the app and SurrealDB: the iOS app (or the web)
calls the database directly, with the rights of the signed-in customer and
nothing more. Why: [DECISIONS.md, section 2](DECISIONS.md#2-no-java-backend-the-api-lives-inside-the-database).
The endpoints are in `schema/07_api.surql`, the sign-in in
`schema/06_access.surql`, and a working client in Python in
`demo/demo_client.py` (official SDK) and `demo/session.py` (plain HTTP).

The examples use namespace `dx`, database `live` and the local server
(`./db/demo/demo.sh up`, port 8099).

## Session

```http
POST /signin
Content-Type: application/json

{"ns": "dx", "db": "live", "ac": "banca", "email": "ana@dominican.test", "pass": "demo-ana"}
```

It returns a token for that customer (keep it in the Keychain on iOS). The app
never holds database credentials: the token only carries that customer's
permissions. Every following request sends `Authorization: Bearer <token>`.

## Reading: SurrealQL, filtered by the database

```http
POST /sql
Authorization: Bearer <token>
surreal-ns: dx
surreal-db: live
Accept: application/json

SELECT * FROM account;
```

The query has no `WHERE customer = ...`: the table permissions already return
only that customer's accounts, movements, cards, contacts and co-holders. The
card number and CVV come back empty unless the customer verified the PIN in
the last 90 seconds (`POST /api/dx/live/verify-pin`).

## Writing: HTTP endpoints inside the database

```http
POST /api/dx/live/transfers
Authorization: Bearer <token>
Content-Type: application/json

{"id": "811DE31E-CA95-4810-BD4C-6EA9B0850F16", "from": "account:ana",
 "to_iban": "ES4444444444444444444444", "amount": "12.50"}
```

```
HTTP 201
{"amount": "12.5", "balance_after": "8413.1", "order": "811DE31E-...", "reason": null, "status": "done"}
```

`POST /api/dx/live/<route>` with a JSON body and the same bearer token:

| Route | Body | Does |
|---|---|---|
| `/transfers` | `{id, from, to_iban, amount, concept?}` | Transfer from one of your accounts (as holder or co-holder) to an IBAN |
| `/bizum` | `{id, to_phone, amount, concept?}` | Bizum from your Bizum account to a phone number |
| `/contacts` | `{phone}` | Add a contact who is a customer |
| `/verify-pin` | `{pin}` | Unlock card details for 90 s; locks after 3 failures |

Formats: phone numbers `+34` and 9 digits, PIN 4 digits, IBAN as stored
(`ES` and 22 digits), `from` as a record id such as `account:ana`, `concept` up
to 140 characters.

Each endpoint checks ownership and limits and answers with real HTTP codes:
201 created, 400 invalid input, 403 not your account, 404 destination not
found, 409 order id already used by someone else, 422 business rule
(insufficient funds, over the limit, same account), 423 account frozen.

Three rules a client must follow:

- **Amounts are strings**, `"12.50"`, never JSON numbers. A number is rejected
  with 400 (`invalid_amount`): binary floating point cannot hold money.
- **Every order carries an `id` generated by the app**, one per payment
  attempt: 8 to 64 characters of `A-Z a-z 0-9 _ -`, so a UUID fits. Sending
  the same `id` again returns the original answer without paying twice.
- **Retry write conflicts with the same `id`.** When two transactions touch
  the same account, SurrealDB undoes one entirely and returns it as HTTP 400
  with "Transaction conflict ... can be retried". Retrying is safe thanks to
  the `id`. Reference implementation: `api()` in `demo/session.py`.

## Alerts in real time

Over WebSocket (`/rpc`), after signing in with the token:

```sql
LIVE SELECT * FROM fraud_alert;
```

The permissions apply here too: each customer only receives alerts on their own
accounts. On a cluster a live query only sees changes made through the node
it is connected to ([CLUSTER.md](CLUSTER.md)).

## In the iOS app

The app reads everything through the `BankRepository` protocol
(`Project/Services`). Two implementations: `MockBankRepository` (fixed demo
data, the default) and `SurrealBankRepository`, which does the calls above with
`URLSession`. Views and view models do not change. Money stays `Decimal` in the
app and travels as text.

`SurrealBankRepository` in one request per screen load: it signs in once, then
sends six SurrealQL statements in a single `POST /sql` (accounts with their
holders, the last 50 ledger entries, cards with what was spent, the customers it
may see, co-holders, notifications). A payment to a contact is a Bizum to that
contact's phone (`/bizum`); a payment to an IBAN is a transfer (`/transfers`).
Each attempt gets a new UUID as order `id`, and a write conflict is retried with
the same `id`. Money requests are not in the database yet and are refused.

### Run the app against the cluster (Xcode)

1. Start the cluster: `./db/demo/demo.sh cluster-up` (HAProxy on `127.0.0.1:8100`;
   the simulator shares the Mac's network, so `127.0.0.1` reaches it).
2. Open `DominicanExpress.xcodeproj`, menu **Product > Scheme > Edit Scheme...**,
   **Run > Arguments**: tick the four arguments already listed
   (`-surreal-url http://127.0.0.1:8100`, `-surreal-db cluster`,
   `-surreal-user ana@dominican.test`, `-surreal-pass demo-ana`).
3. Run on an iPhone simulator. The app shows Ana's real account (balance
   8,425.60 EUR, co-holder Luis), her card ending 4242 and her payroll entry.
4. Bizum: choose **Luis Romero** (the screen preselects a demo name that is not
   a customer, and the database refuses it), amount and send. The balance drops
   by exactly that amount; `./db/demo/demo.sh cluster-status` and the HAProxy page
   (http://127.0.0.1:8404) show the requests reaching the nodes.

`Project/Info.plist` allows plain HTTP only to the local network
(`NSAllowsLocalNetworking`); anything else still needs HTTPS. Untick the
arguments to go back to the demo data.

### Checked without Xcode

The repository compiles in the `DominicanDomain` Swift package
(`swift build`, Swift 6.4, Command Line Tools). Integration tests run it
against a real database through HAProxy:

```sh
./db/demo/demo.sh cluster-up
SURREAL_IT_URL=http://127.0.0.1:8100 SURREAL_IT_DB=cluster ./scripts/test.sh --filter Surreal
```

They check that Ana sees only her account, her co-holder and her card; that a
Bizum of 12.50 to Luis lowers her balance by exactly 12.50; that a wrong
password and a stranger as recipient are refused. Broken on purpose (contacts
query without the filter, amount sent as a JSON number), the matching test
fails. What these cannot check is the interface in the simulator.
